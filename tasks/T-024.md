## Goal

Make the proactive→reactive handoff real: **save** the ring-out result to a file
and **load** it at the start of reactive mode so the static notches are
pre-placed and live protection only defends the remaining margin.

See [`docs/ringout-design.md`](../docs/ringout-design.md) ("One pipeline").

## Acceptance Criteria

- [ ] `--save-profile PATH` (ring-out mode): write the result — per-band notch
      depths (31 bands), measured gain-before-feedback margin, target bus + FX
      slot, mixer model, and a timestamp — as a simple, human-readable text/JSON
      file. Format documented in a header comment.
- [ ] `--load-profile PATH` (reactive mode): on startup, apply the saved notches
      via `send_teq_band` (mark them active so the existing release logic governs
      them), then run normal reactive detection on top.
- [ ] Loaded static notches are distinguishable from live-placed ones (e.g. a
      `from_profile` flag) so a future policy can keep them pinned rather than
      auto-releasing; for v1, document the chosen behaviour.
- [ ] Round-trip test: a saved profile re-loads to byte-identical notch state
      (host test with a fixture file; no mixer needed).
- [ ] Mismatch guard: refuse (clear error) to load a profile whose mixer
      model / bus / FX-slot disagree with the current args, since notch bands and
      routing would not line up.
- [ ] `--help` documents both flags.

## Notes

- This is also the seam for the bigger picture: a ring-out profile is exactly the
  kind of artifact the future "console recall in an Ableton session" idea would
  bind per-song. Keep the format self-contained and portable.
- No new control logic — serialization + apply-on-startup only.
