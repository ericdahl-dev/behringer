## Goal

Make the CLI ToastSaver's RTA *meaningful with a real measurement mic* by
applying a frequency-response correction curve to the `/meters/4` bins — without
adding any audio-capture pipeline. This is the answer to the open question in
`docs/system-tune-design.md` ("measurement-mic guidance / calibration"): keep the
mic on a spare XR18 channel and the CLI a thin OSC client; correct in software.

**Decided (do NOT reopen):** we are *not* routing RTA through the Audient EVO /
on-computer capture. The EVO control is macOS-IOKit-bound and adding capture+FFT
duplicates the XR18 RTA and the iOS/ESP32 FFT path. We reuse the calibration
*curve* (data), not the interface. See the discussion that produced this task.

## Reference (port from friture)

`~/Projects/friture/friture/mic_cal_file.py` + fixtures
`friture/test/fixtures/mic_cal_rew.cal`, `mic_cal_factory.txt`.

Two text formats, both `freq gain` pairs (gain in dB), to support:
- **REW `.cal`**: optional `Sensitivity <x> dBFS` line, then `20 -0.5` / `1000 0.0` rows.
- **Factory `.txt`**: a `*1000Hz <sens>` reference line, then `20.00<TAB>0.1` rows.

Interpolation is **linear in log-frequency**, clamped to the cal range
(`mic_cal_file.py:interpolate_db`). Port that exactly.

## New module: `cli/mic_cal.{c,h}`

Pure C, host-testable (no sockets, no I/O beyond reading the cal text). Suggested:

```c
typedef struct { float freq_hz; float gain_db; } CalPoint;
typedef struct { CalPoint pts[256]; int n; } MicCal;

/* Parse a REW .cal or factory .txt buffer. Returns 0 on success, -1 on parse
 * failure / <2 points. Auto-detects format. */
int  mic_cal_parse(const char *text, int len, MicCal *out);

/* Correction (dB) at an arbitrary frequency: linear interp in log10(freq),
 * clamped to [pts[0].freq, pts[n-1].freq]. */
float mic_cal_at(const MicCal *cal, float freq_hz);

/* Build a per-bin correction array aligned to the RTA. bin_freq[i] = the center
 * frequency of RTA bin i. Fills corr_db[n_bins]; zeros if cal has no data. */
void mic_cal_bin_corrections(const MicCal *cal, const float *bin_freq,
                             float *corr_db, int n_bins);
```

## Apply point

In `cli/XAir_ToastSaver.c::handle_meters4()`, **after** `parse_meters4_blob()`
and **before** detection/baseline: `bins[i] += corr_db[i]`. Load the cal file
once at startup from a `--mic-cal <path>` CLI arg (no arg → zero correction,
current behavior preserved).

## PREREQUISITE — RTA bin → frequency mapping

`mic_cal_bin_corrections` needs each `/meters/4` bin's center frequency, which we
do **not** yet have nailed down (see the meter-research notes: `/meters/4` is
100 bins; the bin→Hz mapping was never empirically confirmed, and `/meters/5`
was an alt candidate). Options, in order of preference:
1. Confirm the `/meters/4` bin→Hz table empirically (tone sweep → which bin lights)
   and hardcode `RTA_BIN_FREQ[100]`. This is also needed by the tune mode (T-021+),
   so it's shared infra — consider splitting it into its own tiny task/module.
2. If `/meters/4` is a fixed 1/Nth-octave layout per the protocol doc, derive it.

Until (1) exists, `mic_cal.{c,h}` + its tests can land standalone (parse + interp
are bin-agnostic); only the apply step is blocked on the frequency table.

## Acceptance Criteria

- [ ] `mic_cal_parse` handles both fixture formats; rejects <2-point / garbage.
- [ ] `mic_cal_at` matches friture's log-freq interp (clamped) within 1e-3 on the

- [ ] `--mic-cal <path>` wired into `XAir_ToastSaver`; absent → identical behavior

- [ ] Correction applied to `bins[]` in `handle_meters4` once the bin→freq table

## Notes

- Detection (reactive feedback) benefits little — baseline tracking already
  absorbs the mic curve. The real payoff is the **response-EQ / tune mode**
  (`system-tune-design.md`), where an uncorrected mic biases the target curve.
- Sensitivity (dBFS) line affects absolute SPL, not the relative shape — only
  needed if/when we report SPL; the per-bin *shape* correction is what matters here.
